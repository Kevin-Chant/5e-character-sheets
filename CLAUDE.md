# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Package manager is **pnpm** (pinned via `packageManager`). Node 22+.

- `pnpm dev` — Vite dev server on http://localhost:3000.
- `pnpm server` — live-edit WAMP sidecar (default port 9000; override with `PORT`). Only needed for real-time sharing; local/Drive storage work without it.
- `pnpm build` — runs `generate-schema` + `type-check` + `vite build` (output `dist/`).
- `pnpm type-check` — `tsc --noEmit`.
- `pnpm lint` (auto-fix) / `pnpm lint:ci` (check only, `--max-warnings 0`). `pnpm lint` accepts optional path args to lint a subset — e.g. `pnpm lint src/lib/rules.ts src/components/build-custom-formula` — defaulting to the whole repo when given none.
- `pnpm pretty` — Prettier write.
- `pnpm test` — Vitest run. Single file: `pnpm test src/lib/utils.test.ts`. By name: `pnpm exec vitest run -t "ordinal"`.
- `pnpm run ci` — schema:check + lint + type-check + test, in sequence. The local pre-push check; GitHub Actions runs the same four as **parallel jobs** (`.github/workflows/ci.yml`), so add any new check to both. **Note:** must be `pnpm run ci`; bare `pnpm ci` hits a reserved pnpm command and fails.
- `pnpm generate-schema` — regenerates `src/schema.json` from the `Character` type. Run after changing the character model (also runs in `build`).
- `pnpm session-smoke` — drive several real browsers through the session flows against a running `pnpm dev` + `pnpm server` and assert what converges. The committed hand-check for the WAMP paths, which jsdom can't reach. `--only <scenario>`, `--headed`, `--slow`, `--shots`.
- `pnpm screenshot` — render a route/fixture to a PNG for visual iteration. **Invoke via `pnpm screenshot` (not `node scripts/...`) and always pass `--out` to your scratchpad** to avoid permission prompts and stray repo PNGs — see [`.claude/docs/screenshotting.md`](.claude/docs/screenshotting.md) (covers the fixtures, flags, and the `#detail`-scroll gotcha).

Full local dev is two processes: `pnpm dev` + `pnpm server`.

## Architecture

A **client-side React 18 + TypeScript SPA** (Vite). There is **no backend database and no accounts** — character data lives only in the browser, the user's Google Drive, or a peer's live session. The Node sidecar (`server/server.js`) is a stateless WAMP message broker, not a data store.

### Storage: the `Datastore` abstraction (`src/datastores/`, interface in `src/lib/types.ts`)

Pluggable backends implementing `Datastore`:

- `local-datastore` — browser `localStorage`.
- `google-drive-datastore` — private chars in Drive `appDataFolder` (filename = uuid) **plus** promoted first-class `*.5echar` docs in My Drive (tagged with `appProperties` markers, see `SHARED_*` in `src/lib/google-drive.ts`). Supports optional `promoteCharacter`/`shareCharacter`/`isShared`.
  - **Sharing rides Drive's own notification email** rather than sending one: the grant and the invitation are the same act, and an app with no backend can't send mail anyway. The one part we control is `emailMessage`, which carries an `/import/<fileId>?name=` link back here (`src/lib/drive-import-link.ts`, route `src/routes/import-character.tsx`) — Drive's own button opens the raw `.5echar`, which is JSON to a human. That link is the document-shaped sibling of `/join/<code>`, and is copyable from the share panel because Drive mail lands in spam.
  - **Account identity rides `about.get`**, not a `userinfo` scope — `drive.appdata`/`drive.file` already reach it, so the signed-in email and storage quota cost no extra consent (`getDriveAccount`, surfaced through the `use-drive-account` module store). The store exists because the "you're in your _other_ Google account" notice is computed exactly once per sign-in — writing the new email down destroys the evidence of the change — so it can't live in a component. `switchDriveAccount()` (GIS `prompt: "select_account"`) is the only route between accounts: the normal sign-in path is silent by design and hands back the same one.
  - **Deleting a promoted document trashes it** (`trashFile`), not `files.delete` — it's a file the user can see in Drive, so "delete" should mean what it means there. Private appData files still delete permanently: that folder's trash isn't reachable from the Drive UI, so trashing one would be equally unrecoverable while still costing quota.
  - It **cannot import unattended, by design**: under the `drive.file` scope a file id is a name we have no right to read until the user picks the file in the Google Picker — that click _is_ the grant. So the link's job is to delete every step around it (sign in via `returnTo`, wait out Drive init, open the Picker pre-queried to the one file via `pickSharedCharacters(query)`), and a second visit skips the Picker entirely because `importedIndex` already holds the file. Widening to `drive.readonly` would make the link self-sufficient at the cost of every user approving read-all-of-your-Drive to accept one sheet.

The active backend is held in `DatastoreSelectorContext` and can be `undefined` (e.g. when joining a remote session — joiners have no local store). `google-drive.ts` holds the raw gapi/REST primitives; the datastore orchestrates caching and promotion. **Drive auth is a module singleton, not a route**: `src/lib/google-auth.ts` owns the config constants, the cached-token store, script loading, silent resume (`ensureDriveToken`), the interactive request (`requestDriveToken`, call it from a user gesture), a proactive pre-expiry refresh timer, and `withDriveAuthRetry` — which every `google-drive.ts` network call rides, so a mid-session 401 gets one silent refresh + retry before surfacing as a typed `DriveAuthError`. React reads it via `useDriveAuthStatus()`. The `/auth` route (`google-auth-initializer.tsx`) is only the interactive consent surface plus the `returnTo` hand-back; nothing needs to detour through it when a silent resume can succeed. The save indicator distinguishes `saveError === "auth"` (a click-to-sign-in button that then retries the save — unsaved edits survive an expired session) from a generic failure.

**Consuming datastores in the UI** — go through the `useDatastore()` hook (`src/lib/hooks/use-datastore.tsx`), not the raw `Datastore` object: it exposes a _reactive_ `characters` list, `characterLoading`, and wrappers like `createCharacter()`/`save()`/`deleteCharacter()` that keep that list in sync. Calling `datastore.listEntriesInDatastore()` directly gives a one-shot snapshot that won't update on create/delete. Two distinct "new character" paths exist: `createCharacter()` **persists** immediately (preferred), while `loadFullCharacter(defaultCharacter)` only loads an unsaved in-memory default. `characterLoading` wraps both the create flow and the initial async list fetch, so guard empty states on it to avoid flashing "no characters" while a backend (e.g. Drive) loads.

**Storage selection is two surfaces, both auto-skippable**: the home page (`src/routes/home.tsx`) picks the _backend_, the character picker (`src/components/character-picker.tsx`, rendered by `sheet-container.tsx` when a datastore is selected but no character is open) picks the _character_. The last-used backend is persisted via `src/lib/last-datastore.ts`, and **the open sheet lives in the URL** — `/sheet/<uuid>` — so a refresh or bookmark lands back on the sheet it left: `sheet-container.tsx` re-selects the remembered backend on a cold start (local instantly; Drive via a background `ensureDriveToken`, detouring to `/auth` only when a click is genuinely needed), then resolves the URL's uuid against the reactive list once it arrives. A stale uuid (deleted, or another Drive account) clears back to the plain picker. The home page doesn't auto-redirect — resume is offered as the front door's "pick up where you left off" links, which point at `/sheet/<uuid>` directly.

### Live editing: a sync _overlay_, not a datastore (`src/lib/hooks/use-sharing-session.tsx`)

Real-time co-editing runs over WAMP (autobahn-browser client ↔ nightlife-rabbit broker). It is independent of where the character is persisted. Key design points that are easy to get wrong:

- **Both realtime layers share one transport**: `src/lib/realm/realm.ts` owns sockets, subscriptions, teardown, and the versioned envelope (`realm/envelope.ts`) — which is where self-echo filtering lives, because nightlife-rabbit does **not** honor WAMP `exclude_me`. The shared presence roster (heartbeats, TTL pruning) is `realm/presence-store.ts`. Both are plain factories with `use-realm.tsx`/`use-presence.tsx` as React wrappers over them — a hook can only hold one of a thing, and the character layer needs one per shared sheet. This layer contributes only its message kinds and roles.
- **A socket that dies without saying so is detected, not waited on.** Mobile networks drop connections without a close frame, leaving a browser that reports "open" while nothing crosses in either direction — indistinguishable, from inside, from a quiet table. The transport therefore registers a procedure named after its own client and **calls it** every 20s: a round trip through the broker over the same socket a real message uses (nightlife-rabbit does not exclude a caller from its own registration). Two consecutive failures — never one, because a resumed tab fires its pending timers at once — count as a close and fire `onClosed`, which is what both layers' recovery hangs off. Messages published into a dead socket are **held and replayed** on the next connection to the same realm, per a `queueWhileOffline` policy each layer supplies: an edit or a roll report is the only copy of itself, while an encounter broadcast supersedes and must not be replayed stale.
- **One sharing session per character**, held in a `Map<uuid, Session>`. This used to be a single `{uuid, role}` — an honest description of a layer that could only hold one socket, and a hazard the moment a DM owns the party's shared sheets: nothing ends a session when you open a different character, so a host looking at sheet B still held sheet A's realm, and A's arriving edits were dispatched into B and autosaved there. Three things make several sessions real: the transport and roster are plain factories (`realm/realm.ts`, `realm/presence-store.ts`) rather than hooks, so a map can hold them — `use-realm.tsx`/`use-presence.tsx` survive as thin `useSyncExternalStore` wrappers for the party layer, which genuinely wants one; every `dispatch` message **carries the uuid it edits**, so `applyRemoteEdit` routes rather than guesses (a message with no uuid to check against is how the scrambling happened, and the outbound `broadcast` and tab-sync's inbound had the check already) — and a routing key that arrives over the wire is checked twice more: **against the session's own uuid**, so a realm can only carry edits for the character it is named for (the broker is unauthenticated; a trusted key is a write primitive for any uuid a peer can name), and, in the reconnect `FULL_SYNC`, **against the sheet actually on screen**, because "the host answered about the right character" and "we are still looking at it" are different questions and a joiner holding a background session had its own sheet replaced by the borrowed one on the first dropped socket; and a session whose sheet **isn't open** still works — `loadStored`/`saveStored` bound up from `CharacterContext` let a host fold an arriving edit into the stored copy through the same pure reducer and serve it to joiners, serialized on a **per-uuid write queue** because read-modify-write against storage otherwise loses whichever of two same-tick edits landed first (the open-sheet check is made on _both_ sides of that read — a Drive round-trip is long enough to open the sheet during — and a fold that fails is **held and surfaced**, `backgroundSaveErrors`/`retryBackgroundSaves`, rather than logged: it is the only copy of a change whose author was told it landed). A _joined_ session whose sheet is closed deliberately writes nothing — the host owns that document, and folding a peer's edit into our copy is the fork the save gate exists to prevent; reopening re-joins and pulls `FULL_SYNC`. Incoming edits are still applied with `suppressBroadcast` to avoid loops. **Navigation never travels**: `isNavigationAction` keeps `load_character`/`reset_character` off both transports, because the uuid a dispatch is published under is the _pre-dispatch_ character's — broadcasting a load sent a whole different sheet into a realm stamped with the uuid peers were editing, and they adopted it.
- **Same-browser tabs sync over a `BroadcastChannel`** (`src/lib/tab-sync.ts`), not over WAMP or storage: the datastores cache and never re-read, so without it a second tab froze at load. Character edits cross as the same dispatch messages the realm carries; an `origin` tag ("local" edits forward into any sharing session the sibling holds for that character, "remote" ones — republished from WAMP — never forward back) is the whole loop story. Sibling edits apply non-dirty: the originating tab owns the write to storage. **Applying and forwarding live in different providers**: applying is `CharacterContext`'s and is gated on the open sheet, forwarding is `SharingSessionsContext`'s because the sessions are — gating the forward on the open sheet too meant a host with a second sheet on screen quietly stopped relaying to its joiners. **The encounter rides the same channel whole** and the receiver _merges_ it through `applyRemoteState`/`receiveState` — two tabs are just two clients who share a localStorage — with the bounce terminated by identity (an unchanged merge doesn't republish).
- **Broadcasting is centralized** in `SharingSessionsContext.broadcast(uuid, …)`; both host and joiner publish over the same transport (bidirectional editing). `CharacterContext` calls it from `dispatchAndBroadcast`, and hands `dispatch`/`getCharacter` plus the `loadStored`/`saveStored` pair up to the provider via `bind` (the provider mounts above `CharacterContext`).
- **Roles**: `host` opens the realm + registers the `FULL_SYNC` RPC (which serves the open sheet when it is the session's, else that character's _stored_ copy — a host holding several sessions is routinely serving one it isn't looking at, so "the open one" is the wrong question); `remote` (joiner) calls `FULL_SYNC`. An _unasked-for_ close starts a **reconnect campaign**, not an ending: the host's explicit `closeSession` is the only instant goodbye, and the retry doubles as the diagnosis — a realm that answers was never gone (our own network dropped), one that reports `absent` for ~30s is one nobody is hosting. Only then does the joiner's character reset. Treating the first dropped socket as "the host ended it" wiped a borrowed sheet and blamed a friend for what was a wifi handover, which on a phone is routine. A joiner that gets back in re-runs `FULL_SYNC` to collect what it missed; a host re-registers it. A `remote` character is **not persisted locally** (the host owns it) — see the role check in `CharacterContext`'s lazy-save. Sync deliberately stays an RPC rather than the play layer's ask-the-room: an owned document has one host who can be asked, and the Drive auto-join retry loop depends on the definite failure that gives.

[`.claude/docs/live-editing-and-presence.md`](.claude/docs/live-editing-and-presence.md) is the deep dive: the two message layers (edit `DISPATCH` sync + best-effort `PRESENCE`/`LEAVE` roster with heartbeats and per-user field highlights) and the role-asymmetric teardown.

### Character model (`src/lib/types.ts`, `src/lib/data/`)

The `Character` type plus 5e data definitions and a recursive **formula engine** for computed fields (AC, HP, attacks). The former grab-bag `src/lib/utils.ts` is split by concern: `src/lib/formula.ts` (the `calculate*`/`format*` engine + `OPERATORS`), `src/lib/rules.ts` (5e domain tables — stat mods, PB, hit dice, spell slots, spellcasting), `src/lib/fields.ts` (dot-path `traverse`/`get`/`setFieldValue` + schema validation), and `src/lib/browser.ts` (secure-context polyfills); `utils.ts` now holds only `ordinal`/`formatClass`. `src/lib/types.ts` is a **barrel over `src/lib/types/`** — `formula.ts` (the `CustomFormula` model), `mechanics.ts` (actions/effects/riders), `character.ts` (the persisted `Character`), `app.ts` (`Datastore`/`Dispatch`) and `guards.ts` (the `is*` runtime guards). Keep importing from `src/lib/types`; import a specific module only when you want the narrower dependency. These pure functions are the main unit-tested surface; Drive/WAMP code is gapi/network-bound and verified manually in-browser (or with throwaway node scripts against a local nightlife-rabbit server).

**Adding or editing a field on the `Character` model** touches several coupled systems (type, `FIELD`/editor registries, default data, generated schema, migration). Two deep-dive docs cover the non-obvious wiring — read them before such changes:

- [`.claude/docs/adding-a-character-field.md`](.claude/docs/adding-a-character-field.md) — the end-to-end checklist (type → schema → migration → UI).
- [`.claude/docs/editable-fields-and-modals.md`](.claude/docs/editable-fields-and-modals.md) — how the targeted-field stack + `ModalContainer` draft buffer turn a field into an editable modal.

The computed-field system has its own deep dive: [`.claude/docs/formula-engine.md`](.claude/docs/formula-engine.md) — the recursive `CustomFormula` model and the two passes (`calculate*` folds to a number, `format*` renders prose), read it before touching `formula.ts` or adding a computed value.

**Spells** get their official content the same way weapons do, but bundled rather than hand-authored: the full SRD catalog is fetched at build time (`pnpm generate-spells`) into `src/lib/data/srd-spells.json` and surfaced — together with the hand-authored non-SRD spells — through a "Browse Spells" picker — see [`.claude/docs/spell-catalog.md`](.claude/docs/spell-catalog.md). Structural spell **damage scaling** (upcast/cantrip tiers) is modelled by an optional `Spell.mechanics` block plus a pure `spellDamageAtLevel` expander that keeps the formula engine untouched — see [`.claude/docs/spell-scaling.md`](.claude/docs/spell-scaling.md). The one engine addition is the `spellMod` `AtomicVariable` leaf (a class's live spellcasting modifier).

**Rolling dice in play** goes through a reusable `RollButton` + a roll dialog that is deliberately _separate_ from the edit modal (rolling is play-mode and read-only) — and a random `src/lib/roll.ts` evaluator kept apart from the deterministic engine. Physical dice are first-class: an in-memory nav-bar toggle (`useRollMode`) flips every roll surface between app-rolled buttons and type-what-you-rolled entry. See [`.claude/docs/rolling.md`](.claude/docs/rolling.md).

**The play surface** (`/play`, `src/components/play/`) is its own route, not a mode of the sheet: the sheet answers "who is this character", a turn asks "what can I do right now". Its core is `src/lib/play/turn-actions.ts`, a **pure projection** that regroups attacks, spells (via `castingTime`) and `LimitedUseAbility` actions by `ActionCost` — so the board is derived, and adding an action means giving something mechanics, never touching the board. Everything on it is **advisory**: the turn economy marks what it saw and can be corrected by clicking, and an action you can't afford dims rather than disabling.

**The encounter** (`src/lib/play/encounter.ts` + `use-encounter.tsx`) is round/initiative/conditions/concentration, and it is **its own local-first object, never a field on `Character`** — a round belongs to no single character, and that separation is what keeps a shared encounter an increment rather than a migration. Its provider sits above the routes so the roll dialog can read conditions from the sheet too. Event recharge ("Dawn", "Initiative") lands in `src/lib/play/triggers.ts` as `planTrigger`, deliberately the same shape as `planRest` — the half of `RechargeCriteria` that rests can't consume.

**Party sessions** (`src/lib/play/session.ts` + `use-play-session.tsx`) share that encounter over a **session-scoped realm** (`sess<hex>`), distinct from the character-sharing realms which are keyed by character uuid. Session codes are **uuids — the uuid is the authentication**, since `openRealm` is unauthenticated and unthrottled; characters remember the ones they've joined (`Character.playSessions`, optional, no migration) because a uuid isn't memorable and a table rejoins weekly. Everyone opens their own character locally and joins a code, so the session syncs the encounter and **never a character** — only a projection (name, initiative, HP, AC, conditions) crosses the wire, which is how the privacy default holds by construction rather than by a flag. Convergence is last-write-wins **per lane, not per document**: the encounter is a declared table of lanes (`ENCOUNTER_LANES`/`PARTICIPANT_LANES` in `src/lib/play/session.ts`) — combat (`round`+`turnIndex`, one atomic pair so two crossed "next turn"s collapse to one), policy, the seat, and five lanes per participant row — each resolved on its own counter, because the DM typing your damage while you tick the spell you're holding is the ordinary shape of a fight, and settling anything shared on one coin flip silently threw one of the two writes away. The coarse `revision` race survives only to decide **roster membership**, whose merge is deliberately bespoke and asymmetric (re-add only your _own_ missing rows — that boundary is what stops a monster the DM removed being resurrected by a stale peer). Publishing back is one loop over the counters (`carriesNews`), and a **joiner adopts the room's state instead of racing it**, because a newcomer's local encounter is an unrelated history that routinely collides on the same revision number and would otherwise discard the fight it just joined. The DM seat is claimed at creation — starting a game _is_ being its DM — and is a UI gate on which controls render, never a lock on who may write, because layer B has to keep working with no session at all. **Entry is the front door** (`src/routes/home.tsx`), which asks what you came to do rather than where your characters live — the old storage-first home auto-redirected returning visitors into their sheet list, which served only the character-builder and hid sessions behind a nav icon. The hub is a resume strip (games this browser played at, from `src/lib/play/session-memory.ts`, plus the last sheet opened, from `src/lib/last-character.ts`), then a code box, then _run a game_ / _my characters_; storage collapses to one door once answered, and there is no Sessions nav button (`/sessions` redirects to `/`). **The lobby is a URL** — `/host` and `/join/<code>` (`src/routes/host-game.tsx`, `join-session.tsx`, both over `components/sessions/session-entry.tsx`) — which is what makes an invite link a link and turns the Drive OAuth round-trip into a plain `returnTo` path. **So is the table itself**: `/play/<code>` is the session's `/sheet/<uuid>`, and a browser that already knows the code reconnects to it on its own (`src/lib/play/rejoin.ts` decides, `hooks/use-auto-rejoin.tsx` wires and retries) — because a phone browser evicts a background tab out of memory unasked, and what comes back is a cold page load mid-fight with everything needed to recover except the name of the table. A code the browser has _not_ seen goes to `/join/<code>` instead, which is where the questions live. Both kinds of code are uuids, so `/join/<code>` probes which realm exists and forwards a shared sheet to `/join`. There are **three lobby shapes, not two**: start a table, rejoin the table you run (which asks nothing — re-bringing sheets would re-snapshot mid-fight monsters to full health), and join someone else's. `hostSession` takes an optional code so a DM can **reopen a table that has gone quiet**, which is what makes a pinned invite link survive the sidecar restarts that every deploy causes. The seat itself is a third lane (`seatRev`), because a client that has never heard of the DM must not be able to erase them — `dmToken` goes with the seat, so that loss is unrecoverable rather than merely unheld. Riding the same realm but never merged into the encounter is the table's **chatter** (`src/lib/play/reports.ts` + `use-table-talk.tsx` — split from the encounter provider by lifetime: born from an arriving message, dead with the socket), chiefly **roll reports**: an attack picks its target _before_ the dice and then publishes each stage as it lands, grouped for the DM by `exchangeId`, so "roll, ask out loud, roll again, then name a target" collapses into one addressed exchange the seat can rule on with Hit/Miss. Re-rolls are **numbered, never blocked** — including one rolled before a target was named, which is held and flushed with its true attempt — because the only honesty available over an unauthenticated broker is visibility, not enforcement. See [`.claude/docs/play-surface.md`](.claude/docs/play-surface.md).

**Ability mechanics** — what features _do_ at the table — are serializable data in `src/lib/mechanics/`: roll **riders** (Durable's minimum, rerolls, crit range) and resource **actions** with action-economy costs (Second Wind, Font of Magic, Lay on Hands), interpreted into ordinary reducer updates so they sync/undo like edits. Adding mechanics for a known feature is a `catalog.ts` entry, not a component. See [`.claude/docs/ability-mechanics.md`](.claude/docs/ability-mechanics.md).

**Rests** are what finally consume `RechargeCriteria`: `src/lib/rest.ts` is a pure planner (`planRest` → a `RestPlan` of reducer updates + a human account of them + the `followUps` the player drives), so the panel in `src/components/rest/` can preview a rest, commit it as a single `replace_character`, then run the interactive parts — spending hit dice, re-preparing spells — against the rested sheet. Rest variants (pacing, hit-dice/HP/exhaustion recovery) are settings on the **Game** tab. Add a rest effect to `planRest`, never to a component. See [`.claude/docs/rests.md`](.claude/docs/rests.md).

**Races / classes / subclasses** for the guided builder are bundled catalog data under `src/lib/data/`, consumed via `src/lib/builder/race-catalog.ts` / `class-catalog.ts` / `subclasses.ts`:

- `srd-races.json` + `srd-classes.json` are **frozen** snapshots of the open-license 2014 SRD — edit the JSON directly (the old `generate-races`/`generate-classes` scripts were retired; only `generate-spells` remains, since the 319-spell set still benefits from regeneration).
- Official content beyond the SRD is **hand-authored** in `nonsrd-races.ts`, `phb-subraces.ts` (extra subraces), `nonsrd-classes.ts` (Artificer), and `subclasses.ts`, then merged into the SRD lists at load time. Keep these files separate from the SRD JSON: SRD prose may be verbatim (open license) but **non-SRD content must store only mechanical facts with original paraphrased summaries** — never published prose. Subclass `grants` apply when the subclass is _chosen_ — at level 1 for cleric/sorcerer/warlock, at the choice level (druid/wizard 2, the rest 3) via the level-up wizard for everyone else. Subclass _pools_ (superiority dice, Healing Light) live in `builder/class-pools.ts` `SUBCLASS_POOLS` instead, so sizes re-derive each level.
- **Racial mechanics are mostly read out of the trait prose**, not duplicated beside it: `build-character.ts` scans traits for resistances, immunities, darkvision, fly/swim/climb speeds, and **natural weapons** (a Lizardfolk's Bite, a Tabaxi's claws → real `attacks`). Write the numbers into the trait's own sentence and the scanner picks them up; the natural-weapon scan deliberately requires the words "natural weapon", which is what keeps a Shifter's while-shifted bite out. Racial _choices_ (Simic Hybrid's Animal Enhancement) are `OptionGroup`s keyed on `race` — see [`.claude/docs/ability-mechanics.md`](.claude/docs/ability-mechanics.md).

- **Tasha's optional class features** — the ones that _replace_ a feature rather than add one — are `src/lib/builder/optional-class-features.ts`, and they're the only grant that makes a level give **less**. A swap is per character (two tables can disagree about editions), offered at the level the feature it replaces arrives at, and **remembered as the feature row it grants**: `takenOptionalFeatures` reads them back off the sheet, which is what lets a swap taken at 1st still suppress a pick at 14th without a field on `Character`. Suppression has three arms — `classFeaturesAt` drops the replaced prose, `OptionGroup` categories named in `replacesOptions` leave `newOptionPicksAt`/`availableOptionGroups` entirely, and a `ClassPoolDef.requiresFeature` gates the pools a swap brings with it. Everything the wizards need to know about which lists are on the table now rides in one `PickContext` (subclass, fighting style, optional features) because all three can be chosen in the same step the picks are offered in.

### State management

React Context + reducers (no Redux). Providers are **deeply nested in `src/index.tsx` and the order matters** — `SharingSessions` sits above `Datastore`/`Character` so broadcast/role state is reachable. Main contexts: `Settings`, `SharingSessions`, `DatastoreSelector`, `Datastore`, `Character` (Drive auth state is not a context — it's the `google-auth.ts` module singleton, read via `useDriveAuthStatus()`). `LevelUp`, `Rest` and `SettingsPanel` sit innermost — each mounts its dialog once and exposes an `open*()`. **Settings is an overlay, not a route**: it was the only interruption in the app you couldn't dismiss, and leaving it cost you your place (flipping a Game setting mid-fight remounted the board). `/settings` survives as a thin alias that opens the panel and redirects, so a stray bookmark and the Drive OAuth `returnTo` still work.

All character edits funnel through one reducer + the `dispatchAndBroadcast` wrapper. [`.claude/docs/character-state-and-edits.md`](.claude/docs/character-state-and-edits.md) explains the write-path: why `update_*` actions carry a field's _whole_ value (which is what makes undo/redo and live-sync replay fall out for free) and the flags that keep local edits, replays, and remote echoes from looping.

## Configuration

All config is optional with built-in defaults. Browser-exposed values use the `VITE_` prefix (required by Vite to reach client code; these ship to the browser and are not secrets):

- `VITE_GOOGLE_CLIENT_ID` / `VITE_GOOGLE_API_KEY` — Google OAuth client + API key (scopes: `drive.appdata` + `drive.file`).
- `VITE_LIVE_EDIT_HOST` — default sidecar URL.
- `PORT` — sidecar port (Node-side, no prefix).

The in-app Settings page persists overrides (e.g. `liveEditHost`) to `localStorage`, and **stored settings take precedence over env/code defaults** — a stale stored host can make the app talk to the wrong sidecar even after changing `.env`.

## Conventions

- Absolute imports use the `src/*` alias (configured in `vite.config.ts` and `tsconfig.json`).
- **Comments are for what the code can't say. Default to none.** This file, and `.claude/docs/`, are where design rationale lives — a comment that re-argues a decision is duplicated prose that goes stale. Before writing one, ask what a reader loses if it isn't there; if the answer is "nothing they couldn't get from the next five lines", don't write it.
  - **Don't write**: narrative history ("this used to be", "a bug where", "we tried X first"); editorializing ("which is what makes this safe", "deliberately", "by construction", bold for emphasis); restatements of the code or of JSX structure; walkthroughs of the lines below; pointers to architecture docs; banner dividers.
  - **Do write**: non-obvious constraints (broker/API quirks, ordering requirements, "keep in sync with X"), the source of a magic number, 5e rules citations that explain an otherwise arbitrary table, and rationale that genuinely can't be inferred — compressed to a clause, not a paragraph.
  - One line beats a block; a file header beats a per-line gloss, and should be one or two lines saying what the module is. If a comment is needed to explain what code does, prefer renaming or extracting until it isn't.
  - When a change makes an existing comment wrong, fix or delete it in the same edit — never leave it as an annotation of what the code no longer does.
- **Nav controls are scoped by surface, not by "is a sheet loaded"** — the matrix is `src/lib/nav-controls.ts` (`navControls`/`navTitle`), consumed by `root.tsx` and pinned by tests. Keying off `character` is what silently gave `/settings` the sheet's entire toolbar once `/play`, `/host` and `/join` became routes. Add a route's controls there, not in a new condition in the nav.
- **Every dropdown is `<Select>` (`src/components/select.tsx`), never a bare `<select>`.** One button that opens a portalled, filterable listbox, with grouping, keyboard nav and a `meta`/`hint` column per option. Filtering is the default rather than an opt-in — the DM's roll call was the only searchable control in the app and it was the one the table liked, while every other list of thirty (conditions, checks, spells, damage types) was a native select you scrolled. The **filter box** is the one conditional part: under `filterThreshold` (8) options it's omitted and typing jumps instead, because a four-item list has nothing to search and an input over it raises a phone keyboard for no reason. Three consequences worth knowing: it takes `label` (there is no `<label for>` to lean on — a wrapping `<label>` forwards nothing to a button, so those became `<span>`s), its `value` is always a **string** (numeric fields wrap with `String()`/`Number()`), and it can't be driven by `userEvent.selectOptions` — tests use `chooseOption`/`openSelect` from `src/lib/fixtures/select-testing.ts`, `scripts/screenshot.mjs` has a `{"choose":[…]}` step, and `session-smoke.mjs` has a `choose()` helper. Free-text fields that suggest (equipment names, damage types, the builder's languages) are a **different** control and still have their own local implementations.
- **Inside the sheet, use `useLoadedCharacter()`** (`src/lib/hooks/use-character.tsx`), not `useCharacter()`: `charsheet.tsx` gates its whole subtree on a loaded character, so the narrowed hook asserts that invariant once instead of every component re-proving it with a `if (!character) return <></>` that can't be taken. Plain `useCharacter()` is for the places where "no character" is a real state — the nav, `sheet-container.tsx`, effects.
- `src/index.css` is a list of `@import`s over `src/styles/*.css`, **in cascade order** — later parts (`ui-refresh.css`, `responsive-sheet.css`) deliberately override earlier ones, so don't reorder or alphabetize them. `src/styles/styles.test.ts` asserts the barrel and the responsiveness contract.
- **Sheet responsiveness is container-driven, not viewport-driven.** Three query containers: `detail` (the sheet's scroll area), `panel` (each of the three main columns), `identity` (the header). Reach for "let it shrink" first — `.row`/`.column` carry `min-width: 0` so flex items can go below min-content — and add a `@container` rule only where content has a real floor and must change _shape_ (a table, six ability boxes). The panel grid's floor in `layout.css` and the restack threshold in `responsive-sheet.css` are a matched pair; move one and you must move the other. Don't add `@media` breakpoints to the sheet.
- **The sheet inherits the paper sheet's _order_; everything else is ours.** The layout deliberately mirrors the official 5e sheet ([the fillable PDF](https://media.wizards.com/2016/dnd/downloads/5E_CharacterSheet_Fillable.pdf)) so a player who has used paper for a decade can scan and jump without a tutorial. That transfer attaches to **relative order and adjacency** — "attacks are under HP", "skills are the left rail" — not to absolute coordinates, which the app can't offer anyway once it restacks. So:
  - **Don't reorder or relocate sections** to put something "above the fold". `src/components/sheet-order.test.tsx` pins the reading order against the paper sheet and will fail if you do. Solve fold problems with _density_ instead (reclaim vertical waste above the thing), which moves nothing relative to anything.
  - **Prominence, density, and affordance are free to change.** Nobody has muscle memory for "death saves are always visible" — they have it for "death saves sit under hit dice". Keep the position, change the weight. Likewise the paper's Inspiration box is a tick, not a number, and the dice buttons have no paper equivalent at all, so there's no memory for them to violate.
  - Restoring **visual hierarchy is pro-fidelity, not anti**: the paper puts AC in a shield and abilities in carved stones, and flattening everything to one rounded rectangle is the bigger departure.
  - **These rules govern the sheet, not every surface.** Rearranging _the sheet_ under a toggle is what costs you: flipping modes to check a proficiency and back shouldn't move anything. A genuinely distinct surface is free — nobody expects the level-up wizard or the play surface to be the sheet, so there's no memory for them to violate. What's ruled out is the middle ground: the same content shuffled into different positions, familiar enough to set an expectation and different enough to break it. (This bullet used to say play mode "never recomposes"; that over-generalised the paper-fidelity argument, which is about a decade of habit built outside the app, into a claim about minutes of habit built inside it.)
- **Tests default to the `node` environment**; a file that needs a DOM opts in with a `// @vitest-environment jsdom` docblock on line 1 (every `*.test.tsx`, plus the three `.ts` files that touch `localStorage` or `window`). Building a jsdom per file used to cost more than running the whole suite. Forgetting the docblock on a component test fails immediately on `document is not defined`, which is why the fast path is the default.
- Component tests render through `renderWithCharacter` (`src/lib/fixtures/render-with-character.tsx`), which supplies the real character/edit-mode/targeted-field/save contexts and applies dispatches through the **real reducer** — so a test can assert the resulting character, not just the action. Don't `vi.mock` `use-character` in new tests.
- ESLint 9 flat config (`eslint.config.mjs`) + Prettier; husky + lint-staged run on commit. `react-hooks/exhaustive-deps` is off.
- `autobahn-browser` ships no types — import with `// @ts-expect-error` and treat connections as the local `Connection = any` alias.
- Changing the `Character` type requires regenerating `src/schema.json` (`pnpm generate-schema`).
